Los secretos de configuración proceden del entorno y no se copian a las tablas. Las URL de resolución se protegen en el almacenamiento del scraper, se entregan solo por el canal interno y no se envían a registros generales, navegador, outbox ni RabbitMQ.

\subsection{Estados}

El estado operativo de una aplicación determina si es visible; una aplicación activa recibe una única clasificación pública generada: \emph{available} cuando existe una fuente directa o \emph{fallback} válida con un candidato descargable, \emph{review} cuando no existe fuente disponible y queda alguna fuente \emph{requires\_manual\_review}, y \emph{missing} en el resto de casos. Las aplicaciones no activas obtienen \ruta{catalog\_status=NULL}. \emph{Pending} puede aparecer en colas internas, pero no es un estado del catálogo ni una solicitud pública.

Los trabajos utilizan \emph{QUEUED}, \emph{RESOLVING}, \emph{DOWNLOADING}, \emph{PACKAGING}, \emph{READY}, \emph{PARTIAL}, \emph{MANUAL\_ONLY}, \emph{FAILED}, \emph{CANCELLED} y \emph{EXPIRED}. Las transiciones válidas se comprueban en el dominio; no se admiten saltos arbitrarios desde controladores o workers.

\subsection{Restricciones e índices}

\begin{itemize}
	\item Índices únicos para slugs, correos, etiqueta normalizada y elemento bundle-aplicación.
	\item Índices compuestos para fuentes por aplicación, sistema, arquitectura, región y estado.
	\item Índices para trabajos por propietario, estado, creación y expiración.
	\item Índices para bundles visibles por tipo, fecha y slug.
	\item Índice compuesto de catálogo por \ruta{catalog\_status}, actualización, nombre normalizado e identificador.
	\item Integridad referencial con eliminación restringida cuando una aplicación participe en trabajos o registros históricos.
	\item Borrado lógico para aplicaciones y bundles cuando sea necesario conservar auditoría.
\end{itemize}

\subsection{PostgreSQL y pgvector}

PostgreSQL contiene una proyección reconstruible y separada de MySQL. Sus tablas son:

\begin{verbatim}
semantic_documents(app_id, content_hash, content, metadata, active, seen_at)
embedding_models(model_version, repository, revision, dimensions,
                 artifact_path, manifest_hash, state)
software_embeddings(app_id, model_version, content_hash, embedding)
embedding_jobs(app_id, model_version, content_hash, status, lease)
semantic_index_state(model_version, index_version, snapshot_hash,
                     expected_documents, indexed_documents, complete)
\end{verbatim}

La clave lógica del vector combina aplicación y versión inmutable de modelo; el \ruta{contentHash} debe coincidir con el documento vigente. Un trigger consulta la dimensión registrada y rechaza vectores incompatibles. El manifiesto del modelo se valida antes de arrancar con pesos locales; no existe descarga dinámica. El estado del índice guarda cobertura y hash del snapshot para que la reconstrucción o el rollback sean controlados.

PostgreSQL participa únicamente en la recuperación de candidatos. Una caída o reconstrucción no modifica el catálogo, la selección ni las descargas; Core vuelve al modo literal. Groq y DeepSeek se usan solamente para descripciones.

\section{Diseño arquitectónico}

\subsection{Capas y puertos del backend}

\begin{description}
	\item[Adaptadores:] controladores REST, clientes internos, Spring Data/JDBC, RabbitMQ, MinIO, SMTP y HTTP externo.
	\item[Aplicación:] casos de uso, transacciones, autorización por propietario, límites y coordinación de outbox.
	\item[Dominio:] agregados de identidad y descarga, reglas, estados, políticas de bundles y objetos de valor.
	\item[Puertos:] contratos para persistencia, publicación, limpieza de artefactos, resolución y notificación.
\end{description}

Las dependencias apuntan hacia las capas interiores. Los adaptadores externos implementan interfaces definidas por la aplicación o el dominio, especialmente para resolución, almacenamiento temporal, colas y proveedores de IA. ArchUnit está declarado como dependencia, pero la entrega no contiene todavía reglas arquitectónicas ejecutables; incorporarlas para impedir accesos directos desde controladores a persistencia es una mejora pendiente.

\subsection{Pipeline del scraper}

El scraper es propietario de Winstall, fuentes, resoluciones, runs y sus colas SQL. El pipeline persistente enlaza \ruta{searcher\_filter}, \ruta{filter\_scraper}, \ruta{scraper\_so\_filter} y \ruta{so\_filter\_descriptor}; sus workers aplican leases, reintentos, backpressure y pausa cooperativa. \ruta{PlatformScraperWorker} obtiene metadatos, candidatos e iconos dentro de su etapa. Los cuerpos y respuestas se definen en OpenAPI. Los errores comparten un esquema con código estable, mensaje público, identificador de incidencia y detalles de validación permitidos. Los parámetros \ruta{os=windows\&os=linux} aplican una unión de plataformas y, cuando están ausentes, equivalen a las tres activas. El parámetro \ruta{status} solo admite \ruta{all}, \ruta{available}, \ruta{review} y \ruta{missing}; cualquier otro valor devuelve 400 con \ruta{invalid\_catalog\_status}. \ruta{searchMode} admite \ruta{lexical} o \ruta{semantic}; omitirlo conserva el comportamiento literal de clientes anteriores. Las respuestas añaden \ruta{requestedMode}, \ruta{appliedMode}, versiones y un motivo opcional de degradación.

\subsection{Propiedad anónima y sesiones}

Cada \ruta{download\_job} tiene exactamente un propietario: un usuario autenticado o el HMAC de una cookie anónima. La cookie \url{BATCH_DOWNLOAD_OWNER} es aleatoria, \emph{HttpOnly}, \emph{SameSite=Lax}, segura en producción y válida durante veinticuatro horas. Una sesión iniciada después de crear un trabajo no elimina el acceso por cookie. CSRF permanece activo también para peticiones anónimas y las notificaciones están desactivadas para estos trabajos. Las sesiones persistentes usan Spring Session JDBC~\cite{springsession}.

\subsection{Eventos y mensajería}

Los exchanges versionados utilizan un sobre con \ruta{eventId}, tipo, \ruta{schemaVersion}, fecha, \ruta{correlationId}, \ruta{causationId} y payload. Los comandos de descarga contienen únicamente \ruta{jobId}, \ruta{itemId}, \ruta{appId} y \ruta{sourceRef}; el worker pide la resolución por un endpoint interno autenticado del scraper. El patrón outbox/inbox, los reintentos exponenciales y la cola DLQ proporcionan entrega al menos una vez sin transportar URL firmadas, cookies ni secretos. El servicio de notificaciones entrega los avisos mediante SMTP~\cite{smtp}.

\section{Diseño procedimental}

\subsection{Creación de un trabajo}

\begin{enumerate}
	\item Autenticar o identificar la sesión anónima.
	\item Validar lista, sistema, arquitectura, región y formato.
	\item Eliminar duplicados y comprobar que las aplicaciones están activas.
	\item Aplicar cuotas y límites conocidos.
	\item Crear \ruta{download\_jobs} y sus elementos en una transacción.
	\item Publicar el identificador en RabbitMQ mediante patrón de salida transaccional o mecanismo equivalente.
	\item Responder con código de aceptación e identificador del trabajo.
\end{enumerate}

\subsection{Resolución segura y revalidación JIT}

\begin{enumerate}
	\item Seleccionar una fuente \ruta{catalog\_available} compatible y mantener únicamente su \ruta{sourceRef} en navegador, outbox y RabbitMQ.
	\item Recuperar el candidato estructuralmente válido por el endpoint interno autenticado.
	\item Si su resolución ha caducado, adquirir el bloqueo y revalidarla justo antes de entregarla al worker.
	\item Validar HTTPS, hostname, DNS, IP y puerto.
	\item Seguir un número limitado de redirecciones repitiendo la validación.
	\item Comprobar destino público final, tipo de contenido, nombre y tamaño.
	\item Persistir resultado y metadatos sin exponer secretos.
	\item Ante éxito, renovar URL y metadatos sin cambiar \ruta{available}; ante fallo transitorio, devolver un error reintentable sin reclasificar; ante fallo terminal, invalidar el candidato.
	\item Dejar que los triggers recalculen fuente, aplicación y contadores; si existe otra alternativa válida, la aplicación permanece disponible.
\end{enumerate}

\subsection{Descarga y reintentos}

Cada elemento se descarga con un máximo configurable de intentos y los fallos temporales utilizan espera incremental. La entrega reinicia el archivo cuando reintenta; una reanudación mediante rangos queda como ampliación posterior.

Durante la transferencia se controla el número real de bytes. Al terminar se compara con el tamaño anunciado cuando existe, se verifica el tipo y se rechaza cualquier archivo que exceda límites, cambie a HTTP o apunte a una red no pública.

\subsection{Compresión y finalización}

\begin{enumerate}
	\item Reunir elementos válidos y errores finales.
	\item Sanitizar y resolver nombres duplicados.
	\item Generar \ruta{manifest.json}; los instaladores se guardan en la raíz y no se crean \ruta{README.txt} ni directorios de errores.
	\item Construir el ZIP en el espacio temporal.
	\item Publicarlo en MinIO con expiración.
	\item Marcar el trabajo como \ruta{READY}, \ruta{PARTIAL} si queda al menos un instalador, \ruta{MANUAL\_ONLY} si solo quedan accesos manuales o \ruta{FAILED} si fallan todos.
	\item Eliminar instaladores intermedios.
	\item Enviar aviso si fue solicitado.
\end{enumerate}

\subsection{Cancelación y limpieza}

La cancelación fija una marca persistente y publica una señal para los workers. Cada fase comprueba esa marca entre operaciones y cierra recursos. El proceso elimina objetos parciales y finaliza como \emph{CANCELLED}. El limpiador busca trabajos expirados y ejecuta una eliminación idempotente.

\subsection{Proyección incremental del catálogo}

\begin{enumerate}
	\item Un cambio de \ruta{resolved\_sources.catalog\_downloadable} suma o resta un candidato en su \ruta{download\_source}.
	\item La columna generada \ruta{download\_sources.catalog\_available} combina estado directo o \emph{fallback}, validación y número de candidatos.
	\item Los triggers de fuente ajustan las contribuciones disponible y revisión de la aplicación; un movimiento resta en el origen y suma en el destino.
	\item \ruta{software\_apps.catalog\_status} aplica la precedencia disponible, revisión y sin instalador, o \ruta{NULL} si la aplicación no está activa.
	\item Los triggers de aplicación aplican incrementos y decrementos atómicos a la fila singleton y aumentan su versión.
\end{enumerate}

La identidad \ruta{total\_count = available\_count + review\_count + missing\_count} está protegida por una restricción. El endpoint de estadísticas ejecuta una lectura por clave primaria, mientras que las consultas combinadas calculan su total sobre el conjunto filtrado. Los comandos \ruta{catalog-projection-check} y \ruta{catalog-projection-repair} auditan o reconstruyen la proyección fuera de las peticiones web.

Los triggers de fuente actualizan también \ruta{software\_apps.version} y \ruta{updated\_at} aunque la categoría no cambie. Así, una transición interna como \ruta{direct} a \ruta{fallback} invalida el token de cambios y refresca la interfaz sin alterar los cuatro contadores.

\subsection{Enriquecimiento y proyección semántica}

El supervisor final del scraper genera descripciones con Groq y DeepSeek, valida el texto y lo persiste. No genera embeddings, recomendaciones ni bundles. El flujo semántico posterior es:

\begin{enumerate}
	\item construir el documento canónico con una allowlist de metadatos y calcular SHA-256;
	\item recorrer el feed autenticado en páginas estables de hasta 500 aplicaciones;
	\item realizar upsert por hash, encolar cambios e inactivar documentos no vistos al cerrar el barrido;
	\item reclamar trabajos mediante lease y generar embeddings con la revisión inmutable seleccionada;
	\item comprobar dimensión, persistir vector y recalcular cobertura;
	\item construir el índice y activar la versión solo cuando la cobertura esperada coincide con la indexada;
	\item atender consultas semánticas; Core degrada íntegramente si falta el modelo, el índice está incompleto o falla cualquier precondición;
	\item conservar el manifiesto y el volumen local para reconstrucción, sin descarga dinámica de pesos.
\end{enumerate}

La activación conserva la versión anterior. El comando administrativo interno puede restaurarla únicamente si sus embeddings siguen cubriendo todos los hashes actuales.

\section{Diseño de seguridad}

Los secretos se proporcionan mediante el entorno o un gestor de secretos. Los contenedores se ejecutan sin privilegios, con sistemas de archivos de solo lectura cuando es posible y límites de CPU, memoria y almacenamiento efímero.

Los logs utilizarán campos estructurados y excluirán contraseñas, claves, cabeceras de autorización, URL firmadas y contenido de instaladores. La auditoría registrará cambios de seguridad sin copiar secretos.

La salida del LLM se considera entrada no confiable: se limita a descripciones, no se renderiza como HTML sin sanitización, no se ejecuta como código y no se convierte en comandos, estados de catálogo o cambios de configuración.

\subsection{Migraciones y propiedad de datos}

Core mantiene identidad, bundles, trabajos y outbox con Flyway; el scraper mantiene catálogo y pipeline con Alembic. En producción los objetivos comprobados son Flyway \ruta{V16} y Alembic \ruta{20260914\_0021}. El cambio de esquema se ejecuta con expand/contract: primero se añaden columnas o tablas compatibles, se realiza backfill y se valida con una copia restaurable; después se observa la aplicación, se comprueban invariantes y consultas y solo entonces se promueve una fase contractiva. Mientras no se supere esa compuerta, las columnas antiguas se conservan y el rollback vuelve al estado anterior.

\section{Diseño de despliegue}

El entorno local utiliza Docker Compose. La composición actual aplica redes internas para las dependencias y permite escalar servicios que no requieren exclusividad mediante \ruta{docker compose --scale}. Incluye:

\begin{itemize}
	\item servicios separados para Core API, scraper, worker, notificaciones, traducciones, búsqueda semántica e indexación;
	\item MySQL compartido por Core y scraper, PostgreSQL/pgvector para la proyección semántica, H2 local para los inbox de worker y notificaciones, RabbitMQ, MinIO y Mailpit;
	\item healthchecks y readiness para ordenar dependencias; Core espera a \ruta{scraper-api} y \ruta{semantic-service}, y los dos motores aplican sus migraciones;
	\item volumen persistente para el modelo local y los artefactos de índice;
	\item comprobaciones de vida y disponibilidad;
	\item límites y solicitudes de recursos;
	\item volúmenes o almacenamiento de objetos para temporales controlados;
	\item secretos fuera de las imágenes;
	\item políticas de red y variables de entorno que restrinjan el acceso entre componentes.
\end{itemize}

El scheduler mantiene exclusividad mediante lock persistente. El escalado automático de workers queda fuera de la composición inicial, pero puede basarse en longitud de cola y datos operativos. Playwright no se escala sin límites, porque cada navegador consume memoria y conexiones externas. La aplicación se despliega actualmente en Oracle mediante Coolify desde Compose/Git; la topología, las variables por categoría, los tags GHCR, las copias OCI y la promoción de migraciones se describen en \href{run:coolify-oracle.pdf}{\ruta{coolify-oracle.pdf}}. No se afirma un servidor Prometheus central ni una campaña de carga.
