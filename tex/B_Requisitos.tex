\apendice{Especificación de Requisitos}

\section{Introducción}

Este documento recoge los requisitos del proyecto. Sus identificadores se relacionan con casos de uso, riesgos y pruebas ejecutadas o pendientes; la existencia de un requisito no implica que se haya verificado completamente.

\section{Actores}

\begin{description}
	\item[Usuario anónimo:] consulta el catálogo, crea selecciones temporales y descarga bundles públicos dentro de cuotas.
	\item[Usuario registrado:] accede mediante enlace de un solo uso enviado a su correo, consulta su panel e historial y mantiene bundles propios públicos o privados.
	\item[Administrador:] mantiene catálogo, fuentes, resolvers, bundles oficiales y estados; revisa colas del scraper, inspecciones manuales y registros.
	\item[Sistema externo oficial:] página o servicio del editor desde el que se resuelve y descarga un instalador.
	\item[Proveedor LLM:] Groq o DeepSeek, utilizado exclusivamente para redactar descripciones largas.
	\item[Servicio semántico:] componente interno que ejecuta modelos de embeddings locales y devuelve candidatos versionados; no decide filtros, permisos ni descargas.
\end{description}

\section{Límites y propiedad de trabajos}

Un trabajo de descarga acepta exactamente una selección de \ruta{appIds} o un \ruta{bundleId}. El servidor resuelve el contenido real del bundle, aplica un máximo de cien aplicaciones y devuelve los contadores solicitadas, aceptadas y omitidas. Cuando no hay ninguna aplicación descargable responde con el error estable \ruta{no\_downloadable\_apps}.

Los usuarios anónimos pueden descargar selecciones y bundles públicos u oficiales. El servidor entrega una cookie \ruta{BATCH\_DOWNLOAD\_OWNER} aleatoria, \emph{HttpOnly} y \emph{SameSite=Lax}; solo guarda su HMAC-SHA-256. El acceso al estado, SSE, cancelación y ZIP exige el usuario propietario o dicha cookie. Los límites iniciales son dos trabajos no terminales, diez creaciones por hora y navegador, treinta por hora y dirección IP anonimizada, cuatro GiB por archivo, veinte GiB por trabajo y ocho descargas paralelas por worker. Las notificaciones SMTP se reservan a usuarios autenticados.

\section{Objetivos generales}

\begin{itemize}
	\item Reducir el trabajo necesario para descargar varias aplicaciones.
	\item Mantener el origen oficial y la trazabilidad de cada instalador.
	\item Evitar almacenamiento permanente y eliminar artefactos temporales.
	\item Permitir reutilizar selecciones mediante bundles.
	\item Facilitar el descubrimiento mediante búsqueda literal o semántica, filtros y bundles mantenidos.
	\item Proteger la infraestructura frente a URL maliciosas y uso abusivo.
\end{itemize}

\section{Reglas de negocio}

\begin{enumerate}
	\item Una selección directa y un bundle son dos entradas alternativas para crear un trabajo. La API exige exactamente una.
	\item Los bundles oficiales se mantienen por rutas administrativas y los bundles propios se gestionan únicamente bajo el UUID de su cuenta, desde el panel personal.
	\item Un bundle oficial solo puede ser creado o marcado como tal por un administrador.
	\item Una descripción larga ausente puede completarse mediante la cola de enriquecimiento. Una descripción manual o personalizada no se sobrescribe automáticamente.
	\item Alembic es el propietario de las tablas del catálogo en el MySQL compartido. Flyway mantiene identidad, bundles, trabajos, outbox y sus proyecciones de Core.
	\item Una aplicación activa pertenece a una sola categoría pública: \ruta{available}, \ruta{review} o \ruta{missing}.
	\item La preferencia de búsqueda se resuelve por URL, después preferencia del usuario y finalmente semántica en la primera visita.
	\item El trabajo parcial será válido cuando incluya al menos un instalador y describa todos los fallos.
	\item La ruta autorizada de Core entrega el ZIP por streaming. El resultado deja de estar disponible tras confirmarse el guardado, cancelarse o cumplirse el límite de inactividad.
\end{enumerate}
