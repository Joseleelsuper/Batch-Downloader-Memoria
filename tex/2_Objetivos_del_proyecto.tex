\capitulo{2}{Objetivos del proyecto}

\section{Objetivo general}

El objetivo general es diseñar e implementar una plataforma web que permita localizar aplicaciones, seleccionar uno o varios instaladores y descargarlos agrupados desde sus fuentes oficiales, evitando el almacenamiento permanente de ejecutables y ofreciendo información clara sobre el origen y el estado de cada archivo.

\section{Objetivos funcionales}

\begin{enumerate}
	\item Construir un catálogo administrable de software con nombre, descripción, etiquetas, página oficial, sistemas operativos, arquitecturas y estado de disponibilidad.
	\item Permitir búsqueda por nombre, editor o descripción y combinarla con filtros de estado, sistema operativo, etiquetas y editor, manteniendo la paginación en el servidor.
	\item Permitir la selección de una o varias aplicaciones. Una selección múltiple se tratará como un bundle temporal para generar un ZIP.
	\item Consultar y descargar bundles mediante enlaces estables y reservar su creación, modificación y eliminación al panel administrativo.
	\item Permitir a los usuarios registrados solicitar la incorporación de una aplicación, proporcionando al menos su nombre y su página oficial.
	\item Proporcionar al administrador funciones para mantener aplicaciones, etiquetas, reglas de resolución, evidencias de fuente y estados del catálogo.
	\item Clasificar cada aplicación activa de forma exhaustiva como disponible, en revisión o sin instalador, manteniendo contadores incrementales coherentes con el catálogo.
	\item Informar del progreso de cada descarga, de los archivos incluidos y de los errores que impidan completar una parte de la solicitud.
\end{enumerate}

\section{Objetivos de descarga y procesamiento}

\begin{enumerate}
	\item Resolver dinámicamente el enlace del instalador desde una fuente oficial mediante una estrategia específica o, como respaldo, mediante navegación automatizada con Playwright.
	\item Validar protocolo, dominio final, redirecciones, tipo de contenido, extensión y tamaño antes de aceptar un archivo.
	\item Descargar los instaladores en el servidor, generar un ZIP con un manifiesto y eliminar todos los archivos temporales al terminar, cancelar o expirar el trabajo.
	\item Procesar las solicitudes de manera asíncrona con RabbitMQ para separar la interacción web de las operaciones de resolución, descarga y compresión.
	\item Aplicar reintentos controlados y permitir un resultado parcial cuando una aplicación falle, manteniendo una explicación individual para cada incidencia.
	\item Calcular, cuando las fuentes lo permitan, un tamaño estimado antes de iniciar el trabajo y aplicar límites por archivo, ZIP, usuario, dirección IP y número de operaciones concurrentes.
\end{enumerate}

\section{Estado de consecución}

La iteración documentada materializa el flujo esencial de catálogo y descarga. El catálogo devuelve los sistemas operativos con un candidato estructuralmente válido y el cliente permite combinarlos con semántica OR mediante parámetros repetidos en la URL. Una comprobación antigua no retira por sí sola una aplicación: la fuente se revalida justo antes de la descarga y solo un resultado terminal explícito modifica su clasificación. MySQL materializa el estado público y sus cuatro contadores mediante columnas generadas y triggers transaccionales.

La creación de un trabajo es asíncrona: el Core persiste el trabajo, sus elementos y el evento de salida en una única transacción; RabbitMQ entrega solo identificadores al worker; y el resultado se publica como progreso, estado terminal y URL temporal de MinIO.

La descarga funciona tanto para selecciones como para bundles. El servidor resuelve un bundle completo, no la previsualización mostrada por la interfaz, impone el máximo de cien aplicaciones y comunica las aplicaciones solicitadas, aceptadas y omitidas. Los trabajos anónimos se asocian a una cookie aleatoria cuyo HMAC se almacena en la base de datos; no se incluyen tokens de propiedad en mensajes, URL ni registros. Los trabajos autenticados y anónimos comparten los estados \emph{QUEUED}, \emph{RESOLVING}, \emph{DOWNLOADING}, \emph{PACKAGING}, \emph{READY}, \emph{PARTIAL}, \emph{FAILED}, \emph{CANCELLED} y \emph{EXPIRED}.

\section{Objetivos de búsqueda semántica}

\begin{enumerate}
	\item Construir un documento canónico por aplicación con nombre, package ID, editor, etiquetas, descripciones, plataformas, arquitecturas, versión y dominio registrado, acompañado de un hash determinista.
	\item Representar esos documentos mediante embeddings locales y mantenerlos en PostgreSQL con pgvector como una proyección reconstruible del catálogo MySQL.
	\item Interpretar consultas en lenguaje natural, enumerar candidatos mediante similitud coseno exacta y fusionarlos con el ranking literal mediante RRF antes de aplicar los filtros ordinarios.
	\item Comparar \ruta{paraphrase-multilingual-MiniLM-L12-v2}, \ruta{multilingual-e5-base} y \ruta{bge-m3}, tanto en estado \emph{zero-shot} como ajustados mediante LoRA y \ruta{MultipleNegativesRankingLoss}.
	\item Seleccionar una versión con train, validación y test separados por aplicación, métricas reproducibles y guardas que impidan empeorar las búsquedas exactas por nombre o package ID.
	\item Degradar de forma íntegra al modo literal ante timeout, error, falta de cobertura o truncamiento; el índice vectorial nunca decide estados, totales o permisos.
\end{enumerate}

\section{Objetivos técnicos y de calidad}

\begin{itemize}
	\item Desarrollar un cliente con React, React Router, Vite, HTML, CSS y TypeScript.
	\item Ejecutar los servicios Java con JDK 26 y generar bytecode Java 25, manteniendo una separación explícita entre Core API, worker de descarga, notificaciones y traducciones.
	\item Documentar la API HTTP mediante OpenAPI, cuyo propósito es describir de forma independiente del lenguaje las capacidades de una API~\cite{openapi}.
	\item Utilizar MySQL para la información transaccional y su proyección incremental del catálogo; mantener PostgreSQL con pgvector como proyección semántica reconstruible.
	\item Ejecutar el scraper sobre CPython 3.14.6 \emph{free-threaded}, comprobar que el GIL continúa deshabilitado tras importar extensiones y reservar los hilos para funciones puras de CPU.
	\item Contenerizar los componentes con Docker y preparar su despliegue compatible con Compose.
	\item Definir pruebas unitarias, de integración, de seguridad, de resolución de enlaces, de generación de ZIP y de extremo a extremo.
	\item Mantener trazabilidad mediante registros de administración, resolución, descargas y uso del asistente.
\end{itemize}

\section{Objetivos de seguridad y sostenibilidad}

El sistema reduce los riesgos derivados de procesar URL externas y ejecutables validando HTTPS, host, puerto, todas las direcciones DNS y la IP efectiva tras cada redirección. Se rechazan redes privadas, reservadas, de enlace local y puntos de metadatos; no se degrada a HTTP. A ello se añaden sanitización de nombres, validación de MIME y firma, control de acceso, CSRF y cuotas de uso. La plataforma no ejecuta los instaladores descargados.

Desde el punto de vista de sostenibilidad, se buscará evitar copias permanentes, eliminar temporales, limitar trabajos innecesarios, reutilizar metadatos válidos y escalar los servicios según su carga. También se atenderá a la accesibilidad, la claridad de la información, la protección de datos y el acceso equitativo a la funcionalidad básica.
