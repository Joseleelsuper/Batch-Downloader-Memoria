\apendice{Manual de programación}

\section{Propósito y alcance}

Este manual describe la estructura actual de Batch Downloader y los procedimientos reproducibles para desarrollarlo. El repositorio principal contiene los servicios, los contratos, la composición Docker y las pruebas. La memoria \LaTeX{} se mantiene en un repositorio hermano para que los documentos puedan compilarse sin introducir herramientas de publicación en las imágenes de la aplicación.

\section{Estructura de directorios}

\begin{description}
	\item[\ruta{services/core-api}:] API Java de identidad, sesiones, catálogo de lectura, bundles, trabajos de descarga y outbox.
	\item[\ruta{services/download-worker}:] consumidor Java que descarga, valida, empaqueta y publica objetos temporales.
	\item[\ruta{services/notification-service}:] consumidor de eventos para plantillas españolas y SMTP.
	\item[\ruta{services/translation-service}:] entrega de locales versionados y caché HTTP.
	\item[\ruta{services/webapp}:] cliente React, TypeScript y Vite, ubicado bajo \ruta{src/main/resources/frontend}.
	\item[\ruta{api/scraper}:] FastAPI, SQLAlchemy, Alembic, proveedores, resolvers, scheduler y colas de enriquecimiento.
	\item[\ruta{services/semantic-service}:] migraciones PostgreSQL/pgvector, búsqueda, indexador y validación del modelo local.
	\item[\ruta{shared/contracts}:] OpenAPI, AsyncAPI y JSON Schema de los mensajes.
	\item[\ruta{docker-compose.yml}:] composición de desarrollo que construye imágenes locales.
	\item[\ruta{docker-compose.ghcr.yml}:] composición que consume imágenes publicadas.
\end{description}

Core y scraper comparten una instancia y una base MySQL, pero no la propiedad de las migraciones: Flyway mantiene identidad, sesiones, bundles, trabajos, outbox y proyecciones de Core; Alembic mantiene aplicaciones, fuentes, resoluciones, colas del pipeline y la proyección incremental del catálogo. El download-worker y notification-service no crean esquemas MySQL propios: cada uno conserva su \emph{inbox} idempotente en H2 sobre su volumen local.

\section{Preparación del entorno}

Se necesitan Docker Desktop con el motor Linux disponible, JDK 26, Maven, Python 3.14 y Node.js. JDK 26 es el runtime; los POM fijan bytecode Java 25. La imagen de producción del scraper compila su propio CPython 3.14.6t. A partir de una copia limpia del repositorio se crea el archivo de configuración y se valida la composición:

\begin{verbatim}
Copy-Item .env.example .env
docker compose --env-file .env config --quiet
docker compose --env-file .env up --build
\end{verbatim}

La variante de imágenes publicadas se inicia sustituyendo el último comando por:

\begin{verbatim}
docker compose --env-file .env `
  -f docker-compose.ghcr.yml up -d
\end{verbatim}

El archivo \ruta{.env.example} no contiene secretos. Para un entorno real deben configurarse, como mínimo, credenciales de MySQL, token interno scraper--worker, claves SMTP, credenciales MinIO y los secretos de sesión y HMAC. Nunca se deben copiar valores reales a \ruta{.env.example}, contratos, trazas o capturas.

\section{Compilación y pruebas}

Las comprobaciones se ejecutan por componente para aislar incidencias. En el scraper se instala primero el entorno declarado en \ruta{requirements.txt}, se instala Chromium para Playwright y se aplican migraciones antes de ejecutar el scheduler:

\begin{verbatim}
cd api/scraper
pip install -r requirements.txt
playwright install chromium
alembic upgrade head
python -m ruff check app tests
python -m pytest -q
\end{verbatim}

El frontend se prueba desde el directorio que contiene \ruta{package.json}:

\begin{verbatim}
cd services/webapp/src/main/resources/frontend
npm ci
npm test -- --run
npm run build
\end{verbatim}

Los servicios Java se comprueban con \ruta{mvn test} en cada módulo. Las cifras de una ejecución no se mantienen duplicadas en este manual: la entrega debe registrar una única tabla final, fechada y asociada al commit verificado. Los avisos de deprecación de dependencias deben registrarse y resolverse antes de actualizar el runtime, pero no sustituyen un fallo de prueba.

Los contratos se validan desde la raíz:

\begin{verbatim}
npx --yes @redocly/cli@1.34.2 lint `
  shared/contracts/openapi/batch-downloader-api.yaml
npx --yes @asyncapi/cli@3.4.2 validate `
  shared/contracts/asyncapi/messaging.yaml
\end{verbatim}

El servicio semántico se comprueba con PostgreSQL/pgvector real. El indexador valida el modelo local aprovisionado y no existe una pantalla de entrenamiento ni descarga dinámica de pesos:

\begin{verbatim}
docker compose --env-file .env run --rm semantic-indexer \
  python -m app.indexer
docker compose --env-file .env run --rm semantic-indexer \
  python -m app.indexer
docker compose --env-file .env run --rm semantic-service \
  python -m app.model_validation
\end{verbatim}

\section{Migraciones y datos}

Core API aplica las migraciones Flyway al iniciar. Producción permanece en Flyway \ruta{V16}; el scraper mantiene Alembic \ruta{20260914\_0021}. Antes de un corte se debe ensayar la transformación sobre una copia restaurable y comprobar conteos, UUID, slugs, claves y proyecciones. La copia antigua se mantiene en modo lectura durante el periodo definido de reversión.

El catálogo se migra exclusivamente con Alembic. Las tablas de cola mantienen un lease, número de reintentos, prioridad, estado y fecha de disponibilidad. No se deben crear ni modificar desde Core API.

La proyección \ruta{catalog\_counters} conserva una fila singleton con total, disponibles, revisión, sin instalador, versión y fecha; las columnas generadas \ruta{download\_sources.catalog\_available} y \ruta{software\_apps.catalog\_status} se mantienen bajo propiedad del esquema. Los triggers propagan operaciones aritméticas por clave primaria desde candidatos a fuentes, de fuentes a aplicaciones y de aplicaciones a la fila global. El código de aplicación nunca actualiza los totales.

Después de una restauración o intervención manual se ejecuta una auditoría fuera de la ruta HTTP:

\begin{verbatim}
cd api/scraper
python -m app.worker catalog-projection-check
# Solo si el informe detecta discrepancias:
python -m app.worker catalog-projection-repair
python -m app.worker catalog-projection-check
\end{verbatim}

Toda migración que cambie la clasificación debe incluir backfill, triggers, invariantes y reparación. Las pruebas adecuadas usan MySQL 8.4 real con Testcontainers y escenarios multifuente, movimientos, borrados, rollback y concurrencia; comprobar únicamente cadenas SQL no verifica el comportamiento de los triggers.

Las migraciones del servicio semántico se aplican desde \ruta{services/semantic-service/migrations}. No se escriben DSN completos en Compose: host, puerto interno 5432, base, usuario y contraseña se inyectan por separado. La tabla de migraciones, la validación de dimensión y los índices parciales se prueban con la imagen pgvector real.

\section{Extender el scraper}

Para añadir un proveedor se implementa \ruta{CatalogProvider} y se registra en el adaptador correspondiente. Para una nueva forma de localizar instaladores se añade una \ruta{ResolverStrategy}; las estrategias existentes cubren endpoints conocidos, GitHub Releases, HTML, páginas de destino y Playwright. Toda estrategia devuelve candidatos, no una descarga aceptada: \ruta{ArtifactFormatRegistry} y el validador determinan extensión, MIME, firma, plataforma y arquitectura. Si no existe evidencia suficiente, la arquitectura se conserva como \emph{UNKNOWN} o \emph{UNIVERSAL}, nunca como \emph{x86\_64} por defecto.

La obtención de iconos forma parte de \ruta{PlatformScraperWorker}; no existe una cola \ruta{icon\_enrichment} ni un endpoint administrativo de backfill. El pipeline persistente enlaza \ruta{searcher\_filter}, \ruta{filter\_scraper}, \ruta{scraper\_so\_filter} y \ruta{so\_filter\_descriptor}. Cada etapa adquiere leases, respeta backpressure y permite pausa cooperativa sin perder los elementos encolados.

Las descripciones se procesan tras \ruta{so\_filter\_descriptor}. El supervisor aplica pausas cooperativas, leases y límites de proveedor. Groq utiliza el modelo y la lista de respaldo configurados; DeepSeek es el último respaldo opcional. Estos proveedores solo redactan descripciones largas: no generan embeddings, no realizan búsquedas y no seleccionan instaladores. Los prompts y claves no se persisten en mensajes de cola.

El documento semántico se construye en el scraper con una allowlist compartida por feed y hash. Al añadir un campo se debe actualizar simultáneamente su esquema, pruebas de determinismo y metodología del snapshot; nunca se incorporan URL completas, secretos o metadatos crudos. El servicio de embeddings usa pesos locales fijados por revisión y manifiesto, pero no descarga pesos dinámicamente ni envía textos o consultas a Hugging Face.

\section{Descargas, mensajes y operaciones}

El Core crea el trabajo, los elementos y el evento outbox en una transacción. \ruta{DownloadJobRequested} contiene identificadores de trabajo, elemento, aplicación y fuente; el worker obtiene la resolución por \ruta{/internal/v1} con \ruta{X-Internal-Service-Token}. El consumidor admite duplicados, respeta la cancelación y publica eventos de progreso y resultado. Los errores de formato se encaminan a DLQ; los fallos transitorios se reintentan por RabbitMQ.

El worker aplica sus propios límites configurables: 100 aplicaciones, 4 GiB por archivo, 20 GiB por trabajo y ocho descargas concurrentes. Antes de entregar una URL resuelta, el scraper revalida bajo bloqueo los candidatos caducados. Un éxito renueva sus metadatos; un fallo transitorio es reintentable y no reclasifica; un fallo terminal invalida el candidato y deja que los triggers recalculen la fuente, la aplicación y los contadores. Una alternativa válida mantiene la aplicación disponible.

El ZIP contiene los instaladores aceptados en su raíz y un único \ruta{manifest.json}; no crea \ruta{README.txt} ni directorios de errores. Si existe al menos un éxito y algún fallo, el trabajo queda \ruta{PARTIAL}; si solo quedan accesos manuales \ruta{.url}, queda \ruta{MANUAL\_ONLY}; si fallan todos, queda \ruta{FAILED}. Después de empaquetar se elimina staging y el resultado permanece temporalmente en MinIO. El limpiador elimina el prefijo de objetos al expirar un trabajo; un error de limpieza se registra, pero no revive el trabajo.

Para diagnosticar una incidencia se correlacionan \ruta{correlationId}, \ruta{causationId}, \ruta{jobId} y \ruta{eventId} en logs estructurados. El panel administrativo expone estado de runs, leases, colas y snapshots; RabbitMQ muestra colas y DLQ, y Mailpit captura el SMTP local. La composición no incluye Prometheus, por lo que no se debe afirmar que existe una pila de métricas desplegada. Nunca se debe pedir una URL firmada, una cookie de propietario o una cabecera interna a un usuario para depurar una incidencia.

\section{Documentación reproducible}

El proyecto de memoria contiene fuentes Mermaid en \ruta{diagrams/}. Cada fuente se renderiza con Mermaid CLI, por ejemplo \ruta{npx --yes @mermaid-js/mermaid-cli -i diagrams/architecture\_containers.mmd -o img/architecture\_containers.pdf}; el mismo nombre base se conserva para SVG cuando se necesite. Los maestros se compilan desde este directorio con \ruta{latexmk -pdf -outdir=build memoria.tex}, \ruta{latexmk -pdf -outdir=build anexos.tex} y \ruta{latexmk -pdf -outdir=build coolify-oracle.tex}. Tras compilar se renderizan las páginas con Poppler para revisión visual. Los tres PDF permanecen juntos en \ruta{build/}; no se copia nada al repositorio principal ni se recrea \ruta{docs/memorie}.
