\capitulo{3}{Conceptos teóricos}

\section{Catálogo centralizado y fuentes oficiales}

Una plataforma de descarga puede almacenar los binarios o limitarse a mantener información para encontrarlos. Batch Downloader adopta el segundo enfoque: conserva metadatos y reglas de resolución, mientras que los instaladores se obtienen bajo demanda. Esta separación reduce la duplicación de ejecutables y evita que el catálogo se convierta en una fuente desactualizada respecto al editor original.

El concepto de \emph{fuente oficial} no se limita a la URL visible de una página. Una descarga puede atravesar redirecciones o terminar en una red de distribución de contenidos. La URL final se comprueba antes de aceptar el archivo: se exige HTTPS, se inspeccionan host, puerto, respuestas DNS e IP efectiva y se rechazan destinos internos o reservados. La interfaz muestra la página oficial, el estado y la fecha de la última comprobación disponible.

\section{Bundles administrados}

Un bundle es una colección identificable de aplicaciones. Puede representar una necesidad concreta, por ejemplo ``herramientas para desarrollo web'', y proporciona un enlace estable para consultar o descargar la selección completa. En la entrega se distinguen:

\begin{description}
	\item[Bundle persistente:] colección creada y mantenida desde la administración y consultable mediante la API pública cuando su estado lo permite.
	\item[Selección temporal:] conjunto de aplicaciones elegido directamente en el catálogo para una descarga concreta.
\end{description}

La API pública permite listar, consultar y descargar bundles; las operaciones de alta, modificación y borrado requieren administración. La autoría comunitaria, clonación, personalización persistente y valoración mediante estrellas se mantienen fuera del alcance implementado.

\section{Resolución de enlaces y scraping}

Las URL de descarga cambian por versiones, regiones, sistemas operativos o decisiones del proveedor. Un \emph{resolver} es el componente que transforma la información de una aplicación y el contexto solicitado en una URL descargable validada.

La estrategia implementada es progresiva y combina información estructurada con navegación controlada:

\begin{enumerate}
	\item consultar las API y datos JSON de Winstall, incluido \ruta{\_\_NEXT\_DATA\_\_};
	\item priorizar la web oficial y resolvers específicos, como GitHub Releases;
	\item analizar HTML y candidatos HTTP con reglas acotadas;
	\item navegar por la página oficial mediante Playwright como último respaldo, inspeccionando enlaces, botones, redirecciones y tráfico de red;
	\item marcar la fuente para revisión manual si no se obtiene un resultado seguro.
\end{enumerate}

Playwright permite controlar navegadores modernos en modo sin interfaz~\cite{playwright}. En el proyecto se encapsula como respaldo de los resolvers de Python; no sustituye a las comprobaciones posteriores. El resultado debe mantener HTTPS, resolver a una red pública, cumplir los límites establecidos y superar la validación del binario.

\section{Procesamiento asíncrono}

Resolver varias páginas, descargar archivos grandes y comprimirlos puede superar el tiempo razonable de una petición HTTP. El procesamiento asíncrono separa la creación de la solicitud de su ejecución.

El Core valida la selección y publica un mensaje mediante un patrón outbox en RabbitMQ. El mensaje transporta exclusivamente identificadores. El worker consume el comando de forma idempotente, solicita al scraper la resolución interna autenticada y actualiza el estado a través de eventos. Spring AMQP proporciona las abstracciones de envío y consumo~\cite{springamqp}. El usuario recibe progreso mediante SSE, dispone de sondeo como respaldo y descarga el ZIP cuando el estado es \emph{READY} o \emph{PARTIAL}.

Los estados previstos para un trabajo son:

	\begin{tabularx}{0.92\textwidth}{p{0.25\textwidth}X}
		\toprule
		\textbf{Estado}    & \textbf{Significado}                                 \\
		\midrule
		\emph{QUEUED}      & Espera de un worker disponible.                      \\
		\emph{RESOLVING}   & Resolución interna de fuentes.                       \\
		\emph{DOWNLOADING} & Descarga temporal y validación de instaladores.      \\
		\emph{PACKAGING}   & Construcción del ZIP y del manifiesto.               \\
		\emph{READY}       & Archivo completo preparado para su entrega.          \\

		\emph{FAILED}      & No se ha podido producir un resultado válido.        \\
		\emph{CANCELLED}   & Trabajo cancelado de forma idempotente.              \\
		\emph{EXPIRED}     & Resultado y objetos temporales eliminados.           \\

\section{Generación temporal del ZIP}

Cada trabajo utiliza un espacio aislado identificado por su código. Los instaladores no se incorporan a un almacenamiento permanente del catálogo. MinIO almacena temporalmente staging, el manifiesto y el ZIP para compartir artefactos entre workers, aplicar tiempos de expiración y evitar que el servidor web mantenga archivos grandes en su sistema local.

El ZIP incluye los instaladores disponibles en su raíz y un fichero \ruta{manifest.json}. El manifiesto registra la aplicación, el sistema operativo, la arquitectura, el nombre del archivo y el resultado del elemento. Si alguna descarga falla, el trabajo puede terminar como \emph{PARTIAL} y conservar el ZIP con los archivos restantes; si no se obtiene ninguno, finaliza como \emph{FAILED}.

\section{Embeddings, búsqueda vectorial y fusión híbrida}

Un embedding es una representación numérica de un elemento en un espacio vectorial. Textos con significado relacionado tienden a ocupar posiciones próximas según una medida de distancia.

PostgreSQL con pgvector permite almacenar vectores y realizar búsquedas de vecinos cercanos mediante distancia euclídea, producto interno o similitud coseno~\cite{pgvector}.

En Batch Downloader el vector no sustituye al registro transaccional. El scraper produce un documento canónico limitado a metadatos públicos y calcula un \ruta{contentHash}; el indexador solo vuelve a generar el embedding cuando cambia ese hash y marca como inactivos los documentos que desaparecen del barrido. Una versión de modelo solo puede activarse cuando todos los documentos activos poseen el vector correspondiente al hash vigente.

La enumeración que delimita el conjunto funcional usa similitud coseno exacta. HNSW se conserva como índice aproximado y se compara con el recorrido exacto durante el benchmark, pero no gobierna facetas o totales. Si la enumeración supera 2.000 candidatos o el índice está incompleto, Core descarta todo el alcance semántico y repite la petición como literal.

La combinación utiliza \emph{Reciprocal Rank Fusion}. Para una aplicación presente en los órdenes literal y semántico se suman términos inversos de su posición con una constante \(k=60\); el peso semántico queda asociado a la versión seleccionada por el benchmark. Después de la fusión, MySQL aplica los filtros estructurales, la regla que sitúa \emph{Revisión} al final, los desempates y la paginación.

\section{Modelo de lenguaje para enriquecimiento de descripciones}

El modelo de lenguaje recibe metadatos acotados de una aplicación para producir una descripción larga. Esta tarea se ejecuta en una cola persistente, fuera del descubrimiento y de la descarga, y su resultado nunca decide si una fuente es segura.

El enriquecimiento admite Groq y DeepSeek mediante una interfaz desacoplada~\cite{groq}. La configuración selecciona el proveedor y los modelos sin modificar la cola ni el catálogo; los límites de concurrencia y cuota impiden que este proceso bloquee el pipeline principal.

Las respuestas se validan antes de persistirse. Las responsabilidades implementadas del modelo quedan limitadas a:

\begin{itemize}
	\item redactar una descripción larga a partir de metadatos existentes;
	\item registrar proveedor, modelo, fecha y error de generación;
	\item respetar una descripción manual y permitir reintentos controlados.
\end{itemize}

El modelo de lenguaje no puede aprobar dominios, resolver una URL, ejecutar descargas, cambiar reglas de scraping ni generar un ZIP. La búsqueda semántica usa modelos de embeddings locales y no incorpora recomendaciones generativas, explicaciones automáticas ni creación asistida de bundles.

\section{Seguridad en la descarga de recursos externos}

El backend recibirá y seguirá URL externas, lo que introduce riesgo de falsificación de peticiones del lado del servidor o SSRF. Un atacante podría intentar acceder a servicios internos, metadatos de infraestructura o redes privadas. La mitigación prevista incluye:

\begin{itemize}
	\item admitir exclusivamente HTTPS;
	\item resolver DNS y rechazar direcciones locales, privadas, de enlace local o reservadas;
	\item repetir la validación después de cada redirección;
	\item no degradar a HTTP y comprobar la red pública después de cada redirección;
	\item limitar redirecciones, tiempo, tamaño y concurrencia;
	\item no ejecutar ningún archivo y sanitizar su nombre antes de incorporarlo al ZIP.
\end{itemize}

También se aplicarán controles de autenticación, autorización, limitación de frecuencia, cuotas y auditoría. Estas medidas evitan que la plataforma se utilice como proxy de descargas masivas y proporcionan evidencias para investigar incidencias.
