\capitulo{4}{Técnicas y herramientas}

\section{Criterios de selección}

Las tecnologías se han seleccionado por su tipado, separación de responsabilidades, facilidad de despliegue, observabilidad y posibilidad de escalar los procesos costosos de forma independiente. La selección se ha contrastado mediante la compilación de los servicios Java, las pruebas del scraper y del frontend, y la validación de los contratos públicos; los resultados de carga en un despliegue público se mantienen expresamente fuera de esta afirmación.

\section{Frontend}

\subsection{React, React Router, TypeScript y Vite}

El cliente utiliza React~18.3 y React DOM para componer la interfaz, React Router~6.30 para representar navegación y filtros en la URL, y TypeScript~5.6 para tipar contratos, estados y formularios. Vite~5.4 proporciona el servidor de desarrollo y la construcción optimizada~\cite{vite}; el plugin oficial de React integra la transformación JSX. Lucide React aporta iconos de interfaz sin introducir una biblioteca de marcas.

HTML y CSS mantienen una tabla compacta y adaptable. Los eventos SSE notifican el progreso de trabajos y WebSocket anuncia cambios del catálogo y de la administración. Los catálogos JSON de idiomas se sirven desde \emph{translation-service} y el frontend conserva un texto español como referencia funcional.

\subsection{Entrega y pruebas del cliente}

La imagen de producción se construye con Node.js~20 y se entrega mediante Nginx~1.27, que sirve los recursos estáticos y enruta \ruta{/api} al Core. Vitest~2.1, Testing Library, jest-dom y jsdom verifican componentes y flujos sin navegador completo; el proveedor V8 produce cobertura. Estas dependencias son de desarrollo y no se incluyen en la imagen Nginx final.

\section{Backend}

\subsection{JDK 26 y bytecode Java 25}

Java es el lenguaje de los servicios del servidor por su sistema de tipos, madurez y bibliotecas. Los contenedores se ejecutan con JDK 26~\cite{java26}, mientras que Maven genera bytecode Java 25. Esta separación evita depender prematuramente del soporte de herramientas de análisis para Java 26 y mantiene una base de ejecución común para Core API, download-worker, notification-service y translation-service.

\subsection{Spring Boot}

Los cuatro servicios Java usan Spring Boot~3.5.16~\cite{springboot}. Sus dependencias directas se distribuyen por responsabilidad:

\begin{description}
	\item[Spring Web MVC y WebSocket:] API REST, SSE, comprobaciones de salud y notificación de cambios del catálogo.
\item[Spring Security, BCrypt y Spring Session JDBC:] autenticación, sesiones persistentes, CSRF, cookies seguras, roles y protección de rutas~\cite{springsession}.
\item[Spring Data JPA y Spring JDBC:] repositorios transaccionales para identidad, outbox y trabajos, junto con consultas explícitas para las proyecciones de catálogo~\cite{springdatajpa}.
	\item[Spring Validation:] validación declarativa de entradas y configuraciones.
	\item[Spring Actuator:] salud, métricas y observabilidad de servicios.
	\item[Spring AMQP:] publicación y consumo de comandos y eventos mediante RabbitMQ.
	\item[Spring Mail:] envío SMTP desde el servicio de notificaciones.
\end{description}

Flyway administra las tablas propiedad del Core; el scraper mantiene las suyas con Alembic. El driver MySQL conecta Core con la base compartida, el SDK de MinIO gestiona objetos y H2 conserva los inbox locales del worker y de notificaciones. \emph{springdoc-openapi}~2.6 expone documentación navegable del contrato.

Las pruebas Java usan JUnit~5, Spring Test, Mockito, AssertJ y Spring Rabbit Test. Testcontainers ejecuta los casos que requieren semántica real de MySQL~8.4~\cite{testcontainers}; H2 se limita a pruebas y a los inbox locales que no dependen de funciones MySQL. JaCoCo~0.8.14 genera cobertura. ArchUnit está declarado en Core, aunque la entrega aún no contiene reglas arquitectónicas activas.

\subsection{OpenAPI}

OpenAPI describe el contrato HTTP versionado bajo \ruta{/api/v1}~\cite{openapi}. AsyncAPI documenta los intercambios RabbitMQ y JSON Schema valida cada evento versionado. Estos contratos se comprueban en integración continua y no se utilizan para realizar scraping.

\section{Resolución de fuentes}

\subsection{Playwright como respaldo del scraper Python}

Playwright controla un navegador en modo \emph{headless} para páginas que requieren JavaScript, interacción o inspección de red~\cite{playwright}. En Batch Downloader se ejecuta desde el scraper Python como último recurso del registro de estrategias, después de los resolvers conocidos, GitHub Releases y análisis HTML. Cada proveedor limita la automatización a pasos conocidos y selectores revisables.

La navegación generalista se mantendrá como mecanismo de respaldo. Los proveedores con procesos complejos podrán disponer de resolvers específicos, de forma que los cambios en una página no afecten al resto del catálogo.

\subsection{Scraper y supervisor de enriquecimiento en Python}

La imagen de producción compila CPython~3.14.6 desde la fuente verificada con \ruta{--disable-gil}. El arranque exige \ruta{Py\_GIL\_DISABLED=1} y \ruta{sys.\_is\_gil\_enabled()=False} después de importar las extensiones nativas; no se utiliza \ruta{PYTHON\_GIL=0} para ocultar una incompatibilidad. FastAPI y Uvicorn proporcionan la API y el servidor ASGI~\cite{fastapi}; Pydantic Settings valida la configuración. SQLAlchemy, Alembic y aiomysql gestionan el catálogo y sus migraciones MySQL~\cite{sqlalchemy,alembic}; aiosqlite se utiliza en pruebas ligeras. La distribución fuente de SQLAlchemy se instala con \ruta{DISABLE\_SQLALCHEMY\_CEXT=1}, tanto en 3.14t como en el control estándar, para usar su implementación Python y evitar que una extensión C reactive el GIL.

HTTPX con HTTP/2 realiza peticiones controladas; selectolax analiza HTML y Playwright~1.61 resuelve páginas que requieren JavaScript. APScheduler inicia ejecuciones periódicas, Tenacity aplica reintentos, tldextract y dnspython apoyan las comprobaciones de dominio y DNS, cryptography cifra las URL, packaging interpreta versiones y structlog produce registros estructurados. Winstall se consulta mediante su API, \ruta{\_\_NEXT\_DATA\_\_} y HTML; GitHub Releases y los recursos de repositorio aportan versiones e iconos cuando existe evidencia suficiente.

Se conserva un único event loop. Un \ruta{ThreadPoolExecutor} acotado recibe exclusivamente parseo HTML, normalización, scoring y deduplicación puros. Las sesiones SQLAlchemy, clientes HTTP, objetos Playwright, eventos, locks y cachés mutables no cruzan hilos. Una segunda imagen 3.14 estándar actúa como control del benchmark con el mismo driver y configuración.

El scheduler adquiere leases y ejecuta \ruta{searcher\_filter}, \ruta{filter\_scraper}, \ruta{scraper\_so\_filter} y \ruta{so\_filter\_descriptor}. El enriquecimiento de descripciones tiene su propia cola persistente; los iconos se resuelven dentro del trabajador de plataforma. pytest, pytest-asyncio y respx cubren el comportamiento asíncrono y HTTP; Ruff y mypy se emplean como comprobaciones estáticas. \ruta{requirements.txt} bloquea las versiones de dependencias de ejecución y prueba para que la imagen y CI sean reproducibles.

\section{Persistencia}

\subsection{MySQL}

MySQL~8.4 almacena los datos transaccionales de identidad, catálogo, fuentes, solicitudes, bundles, trabajos, outbox y pipeline. Core y scraper comparten una instancia, pero cada uno es propietario de grupos de tablas distintos. La clasificación pública del catálogo se proyecta de forma incremental: los triggers trasladan los cambios de candidatos a fuentes, aplicaciones y una única fila de contadores, de modo que el endpoint de estadísticas no agrega las tablas operativas.

\subsection{H2}

\emph{download-worker} y \emph{notification-service} utilizan bases H2 locales para sus inbox idempotentes. Esta persistencia no sustituye MySQL ni representa una copia del catálogo; evita reprocesar mensajes después de un reinicio. H2 también sirve en pruebas Java que no dependen de funciones específicas de MySQL.

\subsection{PostgreSQL, pgvector y servicio semántico}

La composición incluye PostgreSQL~16 con pgvector y un servicio Python independiente. Sus migraciones crean documentos canónicos, versiones inmutables de modelos, embeddings de dimensión variable, trabajos con lease, estado de índices y ejecuciones de benchmark. Los índices HNSW son parciales por versión de modelo; una comprobación en PostgreSQL rechaza cualquier vector cuya dimensión no coincida con el registro del modelo.

El servicio expone una búsqueda interna autenticada y devuelve candidatos, versión de modelo, versión de índice, peso RRF y señal de truncamiento. El indexador reconcilia periódicamente el feed del scraper, actualiza solo hashes modificados y conserva los artefactos anteriores para rollback. MySQL continúa siendo la fuente de verdad efectiva para los datos públicos.

\subsection{Modelos de embeddings y entrenamiento}

Se registran tres revisiones inmutables obtenidas de Hugging Face: \ruta{paraphrase-multilingual-MiniLM-L12-v2} con 384 dimensiones, \ruta{multilingual-e5-base} con 768 dimensiones y prefijos \ruta{query:}/\ruta{passage:}, y \ruta{bge-m3} con 1.024 dimensiones. E5-base es la versión inicial \emph{zero-shot}.

El entrenamiento es un trabajo explícito, nunca una fase del arranque. Produce un snapshot versionado, divide por aplicación y genera consultas navegacionales y de intención con múltiples positivos. Los negativos difíciles se minan dentro de la misma partición, excluyendo todos los positivos y alias exactos. Cada modelo se ajusta mediante LoRA/PEFT y \ruta{MultipleNegativesRankingLoss}; semilla, revisión, configuración, hash del dataset y artefactos se conservan en volúmenes.

La métrica primaria es nDCG@10. También se calculan MRR@10, MAP@10, Recall@10/20, MRR@1 de búsquedas exactas, p50/p95/p99, throughput, RAM, VRAM, tiempo y tamaño de índice y recall HNSW respecto al recorrido exacto. La puntuación de validación pondera un \(70\,\%\) de calidad, \(20\,\%\) de latencia inversa y \(10\,\%\) de memoria e índice. Solo el ganador elegible consulta test una vez.

\section{Mensajería y almacenamiento temporal}

\subsection{RabbitMQ}

RabbitMQ~3.13 desacopla la API de los workers encargados de descargar, comprimir y notificar~\cite{rabbitmq}. Spring AMQP ofrece una abstracción de alto nivel para consumidores asíncronos~\cite{springamqp}. Los exchanges versionados transportan comandos y eventos con \emph{eventId}, tipo, versión de esquema y correlación; la entrega es al menos una vez y los inbox proporcionan idempotencia.

Los mensajes contendrán identificadores, no datos sensibles ni archivos. El estado persistente del trabajo permitirá reintentos controlados y evitará depender exclusivamente de la cola.

\subsection{MinIO}

MinIO almacena temporalmente los ZIP preparados y los objetos intermedios que deben compartirse entre instancias~\cite{minio}. El cliente \ruta{mc} configura el bucket al arrancar, mientras las políticas de expiración y el limpiador eliminan resultados vencidos. No se utiliza como repositorio permanente de instaladores.

\subsection{SMTP y Mailpit}

El servicio de notificaciones consume eventos, conserva su inbox en H2 y envía correo mediante Spring Mail y SMTP~\cite{smtp}. Mailpit~1.30 captura los mensajes en desarrollo y ofrece una interfaz web de inspección; no forma parte del canal de entrega de producción.

\section{Enriquecimiento mediante LLM}

Groq y DeepSeek se utilizan exclusivamente para generar descripciones largas. El scraper no expone directamente el proveedor al resto de módulos: una interfaz de generación y una estrategia de fallback permiten cambiar modelo, proveedor o límites sin modificar la cola. Se registran el proveedor, modelo, hash de entrada, fecha y error; una descripción manual no se sustituye automáticamente. Los embeddings se calculan localmente en el servicio semántico y no reutilizan estos proveedores.

\section{Contenedores y despliegue}

\subsection{Docker}

Cada componente se empaqueta en una imagen Docker~\cite{docker}. \ruta{docker-compose.yml} construye el árbol local y \ruta{docker-compose.ghcr.yml} consume imágenes publicadas en GHCR. La composición incluye Nginx, Core, scraper API y scheduler, worker, notificaciones, traducciones, servicio e indexador semánticos, MySQL, PostgreSQL/pgvector, RabbitMQ, MinIO/\ruta{mc} y Mailpit. El entrenador y los dos controles de benchmark pertenecen a perfiles explícitos. Los healthchecks ordenan migraciones y arranque sin mezclar la propiedad de esquemas ni confundir el puerto publicado de PostgreSQL con su puerto interno 5432.

\section{Herramientas de desarrollo y documentación}

Git mantiene el control de versiones. Maven~3.9.16 compila y verifica el reactor Java; npm usa el lockfile del frontend. GitHub Actions valida contratos, pruebas y construcción, publica imágenes en GHCR y ejecuta el análisis configurado para SonarQube~\cite{sonarqube}.

La memoria se mantiene con \LaTeX{}, pdf\LaTeX{}, latexmk y BibTeX. Mermaid CLI~11.12 es la fuente editable de los diagramas; Puppeteer utiliza Chromium para renderizarlos en SVG y PDF. Los scripts PowerShell reproducen el proceso y Poppler aporta \ruta{pdfinfo}, extracción de texto y conversión a PNG para la inspección visual final.
