\apendice{Plan de Proyecto Software}

\section{Introducción}

Este anexo registra la planificación aplicada para transformar el diseño de Batch Downloader en una aplicación verificable. Las semanas iniciales sirvieron para ordenar dependencias; la tabla se conserva como trazabilidad y se complementa con el estado real de los entregables.

El trabajo sigue un enfoque iterativo. Cada fase termina con pruebas automatizadas y actualización de la documentación. Las funcionalidades de inteligencia artificial y despliegue distribuido se subordinan al núcleo de descarga, seguridad y limpieza temporal.

\section{Metodología}

Se utilizará un tablero de tareas con una lista priorizada y ciclos semanales. Cada elemento deberá incluir descripción, criterios de aceptación, riesgos y pruebas. Una tarea se considerará terminada cuando:

\begin{itemize}
	\item el código esté integrado en la rama principal del proyecto;
	\item las pruebas relacionadas sean reproducibles;
	\item no exponga secretos ni datos personales;
	\item la documentación afectada esté actualizada;
	\item el flujo pueda demostrarse en el entorno de desarrollo.
\end{itemize}

Las revisiones con los tutores se utilizarán para confirmar alcance, arquitectura y presentación de resultados. Los cambios relevantes se registrarán como decisiones de arquitectura para evitar que la memoria y la implementación evolucionen de forma contradictoria.

\section{Estado de ejecución}

Se han completado el catálogo, los filtros por sistema operativo, sesiones y roles, trabajos asíncronos, almacenamiento temporal, lectura pública y mantenimiento administrativo de bundles, contratos y el pipeline persistente del scraper. La clasificación del catálogo se materializa mediante columnas generadas, triggers y una fila singleton de contadores en MySQL. La búsqueda híbrida utiliza embeddings locales y una proyección pgvector; Groq y DeepSeek solo enriquecen descripciones. Las funciones comunitarias de bundles permanecen fuera del alcance funcional.

El núcleo se ejecuta en pruebas focalizadas de Core API, worker, notificaciones, traducciones, scraper, servicio semántico y frontend. La aceptación exige además MySQL 8.4 y PostgreSQL/pgvector reales, casos multifuente, fallback íntegro y una inspección completa del navegador. Permanecen como trabajos posteriores una campaña prolongada de carga y el despliegue público.

\section{Hitos}

\begin{description}
	\item[H1 - Catálogo utilizable:] un administrador puede registrar aplicaciones y un usuario puede buscarlas.
	\item[H2 - Descarga segura:] una selección genera un ZIP desde fuentes validadas y elimina los temporales.
	\item[H3 - Bundles administrados:] los usuarios consultan y descargan bundles visibles; los administradores los crean y mantienen. Las funciones comunitarias previstas no se completaron.
	\item[H4 - Búsqueda semántica:] el catálogo ofrece modos literal e híbrido, con modelos versionados, evaluación, cobertura completa y fallback.
	\item[H5 - Entrega:] el sistema se despliega, se prueba y los manuales reflejan el comportamiento real.
\end{description}

\section{Estudio de viabilidad}

\subsection{Viabilidad técnica}

Las tecnologías seleccionadas disponen de documentación, bibliotecas para Java y ejecución mediante contenedores. El principal riesgo técnico no es la disponibilidad de herramientas, sino la variabilidad de las fuentes externas y el tratamiento seguro de descargas. Por este motivo se requiere un prototipo temprano con varias páginas de distinta complejidad.

La arquitectura puede simplificarse para el desarrollo local: un frontend, una aplicación Spring modular, un worker y servicios Docker.

\subsection{Viabilidad legal}

La plataforma tratará cuentas, direcciones IP, registros y solicitudes, por lo que deberá cumplir el Reglamento General de Protección de Datos~\cite{rgpd} y la Ley Orgánica 3/2018~\cite{lopdgdd}. Se aplicarán minimización, limitación de finalidad, plazos de conservación, información al usuario y mecanismos para ejercer derechos.

Si se presta como servicio web, deberán publicarse la identificación del responsable, condiciones de uso, política de privacidad y política de cookies conforme a la Ley 34/2002~\cite{lssi}. Los correos solo se enviarán para finalidades solicitadas y con mecanismos para evitar abuso.

Los instaladores pertenecen a sus respectivos titulares. Batch Downloader no alterará ni redistribuirá copias permanentes; los procesará temporalmente desde fuentes oficiales para atender una solicitud. Aun así, antes de incorporar cada aplicación deberán revisarse sus condiciones de uso y las limitaciones de automatización. La Ley de Propiedad Intelectual constituye el marco general español aplicable~\cite{propiedadIntelectual}.

El código propio se publica bajo GNU GPL 3.0, tal como declara el repositorio. La memoria conserva su licencia documental actual. Los nombres y logotipos de terceros se utilizan únicamente con finalidad identificativa y respetan sus marcas y condiciones de uso.

\section{Criterios de seguimiento}

El avance se medirá por hitos demostrables y cobertura de riesgos, no únicamente por número de funcionalidades. En cada revisión se registrarán tareas completadas, incidencias abiertas, pruebas fallidas, decisiones pendientes y desviación respecto a la planificación. Si el calendario se reduce, se protegerán primero la seguridad, la descarga temporal, la trazabilidad y el fallback literal; el entrenamiento intensivo o el despliegue avanzado se reducirán antes que degradar esas garantías.
